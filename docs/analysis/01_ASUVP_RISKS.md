# АСУ-ВП: риски, пробелы, итог

Источники: [01](01-asuvp-hourly-import.md), [03](03-oracle-plsql-jobs.md), [09](09-function-gap-matrix.md), [10](10-target-architecture-migration.md). Промышленный FTP и Oracle не вызывались. Импорт не запускался.

## Риски

1. **Две копии сервиса.** У «Сервис приложение» импортёры включены и маска RU `disl_operations*.txt`, каталог `///tisservice//disl_vagons_tmp//`. У «Сервис пользователя» импортёры выключены, маска RU `disl_cis*.txt`, каталог `//Infoservice//`. Включение импорта на API-копии снимет другой набор файлов.
2. **Опрос 45 секунд и ~18k строк.** Таймер не равен часу. Пока `IsImportedFile` возвращает ложь, каждый тик снова вызовет `ProcessFile`. При ошибке самой проверки метод возвращает `false` и не блокирует повтор.
3. **Частичный импорт не откатывается.** TXT-путь без транзакции. Сбой на строке N сохраняет уже отправленные строки. Если пакет помечает файл импортированным в `SaveImportFile`, повтор этого имени не произойдёт, и час останется неполным. Файл при этом уже лежит в `processing` и следующим опросом входного каталога не читается.
4. **Нулевой идентификатор.** `SaveImportFile` / `SaveStateReport` при ошибке возвращают `0`, и цикл строк всё равно идёт.
5. **Пустой файл и копия на TIS.** Нулевой файл удаляется, но при `CopyTisServiceDislocation=True` `UploadFile` вызывается после удаления.
6. **«Все 18 000, включая неизменившиеся» зависит не от сервиса.** C# пишет каждую строку файла. Нет ли отсечения в `ImportPkg.SaveStateReportLineKz` — неизвестно. `wagons.txt` (18334 строки) — список публикации `GivingDeparture`, не таблица срезов.
7. **Путаница полного файла и дельты.** `disl_operations*.txt` — канал RU тип 1, не доказанный файл изменений KZ.
8. **Параллельный новый импортёр.** Пока пакет не прочитан, второй писатель в тот же `ImportPkg` может задвоить срез или создать задания `CreateJobUpdate*` (этап 10: старый импортёр остаётся единственным писателем).
9. **Сырой поиск литералов расходится с декомпиляцией.** `ilspycmd` показывает `ImportPkg.SaveStateReportLineKz` и `wagons.txt`. Отдельный просмотр байт UTF-16/ASCII по дереву «Старая программа» эти строки не нашёл. Опора документов — декомпиляция, не байтовый поиск.

## Подтверждено

- Импорт срезов выполняет «Сервис приложение», классы `RemoteLib.GivingDepartures.ImportStateReportsFtp` и наследники. «Сервис пользователя» эти задачи выключает и отдаёт Remoting НУВ.
- Таймер KZ: секунды, эталон 45. Маска `disl_kz*.txt`. Тип в поле класса равен 0, потому что `STATEREPORTS_KZ_TYPE` не присваивается.
- Порядок: `IsImportedFile` → `SaveImportFile` → `SaveStateReport` → каждая строка `SaveStateReportLineKz` → `UpdateStateReport`. Пустой файл удаляется и не регистрируется.
- В C# нет сравнения с прошлой дислокацией и нет отдельного алгоритма дельты.
- Ошибка строки не останавливает файл. Транзакции на весь TXT нет.
- Чтение в НУВ: `GivingDeparture.GetWagonStateReports` → `StateReports.LoadWagonStateReports` → `StateReportPackage.GetWagonStateReports` (сутки 00:00:00–23:59:59).
- `wagons.txt` формирует `GivingDeparture.PublishRegistryStateReports` / `PublishRegistryStateReportsThird`.

## Неизвестно

- Тела `ImportPkg.SaveStateReportLineKz`, `SaveStateReportLineRu`, `UpdateStateReport`, `IsImportedFile`: пишется ли неподвижный вагон и когда файл считается импортированным.
- Имена таблиц, ключи, партиции, срок хранения, фактический объём.
- Содержимое реального `disl_kz*.txt` и существует ли отдельный файл изменений KZ.
- Создаёт ли `UpdateStateReport` серверные задания.
- Совпадает ли тестовая `dbtc` с этим набором процедур.
- Почему байтовый поиск не видит литералы, которые показывает декомпилятор.

Read-only словарь тестовой `dbtc` по `ImportPkg` и `StateReportPackage` (тексты процедур, таблицы, триггеры). Без промышленного подключения и без запуска импорта. Образец полного файла и, если он есть, файла изменений — отдельно от кода. До этого новый писатель среза не подключать (этап 10).
