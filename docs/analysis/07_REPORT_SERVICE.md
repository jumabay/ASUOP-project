# Сервис пользовательских отчётов

Разбор сделан декомпиляцией `ilspycmd` 9.1 по копиям сборок. Оригиналы в «Старая программа» не менялись. Клиенты не запускались. Пакеты Oracle не выполнялись. Тела `PACKAGE BODY` скрыты: алгоритм внутри процедуры назван только там, где его видно в spec или в клиенте.

Исходников `.sln` / `.cs` у отчётного контура нет. Эталон сборок: `Старая программа/Сервис пользователя/ApplicationService/ApplicationService/`. Та же `ReportingLib.dll` лежит в «Сервис приложение» и в каталогах УВП, НУВ и НУД.

## 1. Структура, технологии, зависимости

Отдельного процесса «сервис отчётов» нет. Пользовательский отчёт собирает клиент, а текст SQL исполняет общий модуль базы `RemoteLib.DbManagerCall` внутри Windows-службы `ApplicationService.exe` **1.0.3.37**.

| Сборка | Версия файла | Роль в отчётах |
| --- | --- | --- |
| `ApplicationService.exe` | 1.0.3.37 | хост Remoting |
| `RemoteLib.dll` | 1.0.0.0 | `DbManagerCall.GetData`, список потоков отчёта |
| `WagonLib.dll` | 2.1.7673.42322 | конструктор, `QueryBuilder`, условия, просмотр |
| `ReportingLib.dll` | 1.0.2.0 | готовые отчёты, экспорт в Excel через COM |
| `PlannerLib.dll` | 1.0.2.0 | корни конструктора НУВ и четыре готовых отчёта |
| `WarehouseLib.dll` | 1.1.2.0 | корень конструктора НУД |
| `PlatformStateReports.dll` | 1.0.0.0 | задание-заглушка |
| `JobsLib.dll` | 1.0.0.0 | интерфейс задания, не планировщик отчётов |
| `CustomControlsLib.dll` | — | перечисления операций, масок, группировок |
| `DBManagerLib.dll` | — | сохранение объектов через процедуры; произвольный SQL отчёта идёт мимо него |

Стек: .NET Framework, WinForms, .NET Remoting (`tcp`, объект `IDbManagerCall`, порт атрибута **5505**), `System.Data.OracleClient`, DevExpress 20.2 (сетка, сводная, график), `Microsoft.Office.Interop.Excel`. Схема соединения — та же, что у службы (`dbtc` в `config.json`). Отдельной базы отчётов нет.

Две копии службы различаются `config.json` (импорт срезов и сообщения). Код отчётов у них общий.

## 2. Как создаётся пользовательский отчёт

Конструктор — `WagonLib.Reporting.ReportConstructor.ReportConstructorForm`. В него передаётся экземпляр наследника `Report`. Наследник задаёт корень `FROM` и номер приложения, по которому из Oracle читается дерево полей.

Дерево полей: `TableFieldGroup.LoadRoot(applicationId)` вызывает три процедуры с одним параметром `applicationId`:

- `ReportingPackage.GetGroups`
- `ReportingPackage.GetTables`
- `ReportingPackage.GetFields`

Пользователь переносит поля из дерева в список отчёта, задаёт условия, признак «выводить», группирующую функцию, арифметику и маску. Сводка и график — вкладки DevExpress; раскладка сохраняется байтами внутри отчёта.

Сохранение — локальный файл, не строка в Oracle:

| Расширение | Формат |
| --- | --- |
| `.rep` | `SoapFormatter` |
| `.brp` | `BinaryFormatter` |

Диалог по умолчанию предлагает `.rep`. При открытии тип файла должен совпасть с типом конструктора (`report.GetType() != reportType` — отказ).

Повторный запуск сохранённого отчёта с информационной панели: объект `Report` лежит в реестре Windows (`staticInfoPanel.LoadFromRegistry`). Это не каталог в базе. Экземпляры пользовательских файлов в поставке не лежат, поэтому перечень «какие отчёты люди сохранили» из исходников не восстанавливается.

Кнопка «Получить отчет» открывает `ReportViewerForm` и вызывает `Report.GetResultTable()`. Метод `GetCount()` в просмотре не вызывается. Методы `Report.Execute`, `Cancel`, `Refresh`, `Check` пустые.

Асинхронный контур не дописан. `DbManagerCall.ExecuteReportData`, `CancelReportData` и `CheckReportData` бросают `NotImplementedException`. Класс `ReportThread` хранит текст запроса и `Guid` сессии, но `ReportThreadsList.Add` в разобранных сборках не вызывается. `SecurityCall` умеет стартовать, остановить и убить поток из этого списка; при пустом списке это не запускает отчёт.

## 3. Как собирается SQL

`QueryBuilder` склеивает одну строку и отдаёт её в `Session.Current.DbManager.GetData`. На клиенте это `RemoteDbManager.GetData`: строка уходит на службу без разбора. Служба выполняет её так:

```text
OracleCommand
  Connection  = соединение сессии
  CommandType = Text
  CommandText = query
OracleDataAdapter.Fill
```

Параметров `OracleParameter` у этого текста нет. Значения фильтров уже вшиты в строку на клиенте.

Состав запроса данных:

1. `SELECT` и список полей с псевдонимами `Name0`, `Name1`, …
2. Корень `FROM`, заданный классом отчёта.
3. Фрагменты `JoinString` таблиц выбранных полей. Служба отдаёт их в верхнем регистре. Одинаковые куски `INNER JOIN` / `LEFT OUTER` / `RIGHT OUTER` добавляются один раз.
4. `WHERE`, если есть условия.
5. `GROUP BY`, если хотя бы у одного выводимого поля функция не `None`.

Поле, у которого `Table == null`, в SELECT не попадает. Если имя поля в метаданных начинается с `(`, в запрос берётся имя целиком, без префикса таблицы. Так в каталог полей можно положить готовое SQL-выражение. Сам каталог в этой поставке не выгружался.

Арифметика числа (`FieldOperation`) подставляется вокруг поля: сложение, вычитание, умножение, `round(поле/значение, 2)`, `round(поле, значение)`. Операнд `Value1` — строка, в запрос она попадает как текст.

Маска в SQL есть только для дат: `to_date(to_char(...))` с форматами `dd.mm.yyyy`, `hh24:mi:ss`, дата и время, дата и часы-минуты, `mm.yyyy`. Маски целого и дробного числа в `QueryBuilder` не применяются.

Группировка в SQL: `SUM`, `MAX`, `MIN`, `COUNT`, `round(AVG(...), 2)`. Поля без функции попадают в `GROUP BY` уже после маски даты.

Отдельный запрос кодов вагонов (`BuildCodesQuery`) есть только у `WagonReport`: `SELECT wagon.id, wagon.code, WAGONTYPES.COLOR ... ORDER BY WAGON.CODE`, с добавлением `LEFT OUTER JOIN WAGONTYPES`, если его ещё нет в `FROM`. У запроса данных `ORDER BY` нет.

`BuildCountQuery` строит `SELECT COUNT(*)` с тем же `FROM` и `WHERE`. Вызовов `GetCount()` из форм не найдено.

Готовые отчёты (раздел каталога) идут другим путём: `ExecuteNonQueryCursor(имя_процедуры, словарь)`. Там `CommandType.StoredProcedure`, значения — параметры команды. Это не конструктор.

## 4. Фильтры, сортировка, группировка, формулы

Условия — классы `WagonLib.Reporting.Conditions.*`. Несколько условий одного поля всегда соединяются через `OR`. Между полями стоит `LogicalOperator` предыдущего поля: `AND` или `OR`. Поле без условий всё равно обновляет этот оператор для следующего поля.

| Условие | Что попадает в SQL |
| --- | --- |
| Строка | значение в кавычках; «начинается / содержит / кончается» — `LIKE` с `%`; «из массива» — `IN` из слов, разделённых пробелом |
| Число, интервал числа, длительность | оператор и число через точку как десятичный разделитель |
| Массив чисел | токены после `Split()` без разбора в число |
| Дата и интервал дат | `to_date('dd.MM.yyyy HH:mm:ss', ...)` |
| Справочник | `таблица.Id` и числовой идентификатор элемента; «пусто / не пусто» — `IS NULL` / `IS NOT NULL` по `Id` |
| Логическое | `= 1` или `= 0` |

Операторы сравнения: равно, не равно, больше, меньше, больше или равно, меньше или равно, начинается с, содержит, кончается на, из массива, не из массива, пусто, не пусто, четыре варианта интервала.

Сортировка результата в SQL конструктора отсутствует. Порядок меняет сетка DevExpress уже в памяти и сводная таблица. Единственный `ORDER BY` конструктора — коды вагонов.

Группировка — функции выше и клиентская сводная (`ReportPivotControl`). Итог «ИТОГО» по календарю погрузки считается в `CalendarLoadingReport` уже в `DataTable`: сумма целочисленных колонок дней.

Формулы конструктора — арифметика `FieldOperation` и выражения метаданных, имя которых начинается с `(`. Формул Excel в конструкторе нет.

Проверка полей (`CheckReportFields`) заново ищет поле по заголовку и полному имени. Обход дерева возвращает результат первого вложенного узла и не смотрит соседние группы.

## 7. Фоновые задания

Пользовательский отчёт по кнопке выполняется в вызове `GetData`, не в планировщике.

На службе:

- `PlatformStateReportsJob.Run/Stop/Setup` бросают `NotImplementedException`. Имя задания — «Обновление данных по платформам», описание упоминает MS SQL. Кода обновления нет.
- `ExecuteReportData` не реализован, потоки отчёта в список не добавляются.

В Oracle (каталог jobs уже снят в разборе схемы, здесь jobs не запускались) данные для отчётов готовят чужие задания:

| Job | Когда | Процедура |
| --- | --- | --- |
| `FILLGIVINGREPORTS` | ежедневно 01:00, ENABLED | `GivingDepartureReports.FillGivingReports2` |
| `FILLKPI` | ежедневно 02:00, ENABLED | `KpiPkg.FillKpi` |
| `AVAILABILITY_VIEW_JOB` | ежедневно 12:00, ENABLED | `ResourcePkg.UpdateAvailabilityView` |
| `UPDATEALLREPAIRDATES` | ежедневно 01:00, ENABLED | `JobPkg.UpdateAllRepairDates` |

`GivingDepartureReports` в spec ещё содержит `FillGivingReportsOldPeriod`, `RefreshGivingReports`, `RunRefreshJob`. Это запись производных данных, не конструктор. `FILLGIVINGREPORTSOLDPERIOD` в каталоге jobs выключен или в ошибке.

Импорт срезов FTP (45–60 с) пишет `STATEREPORTRECORDS`, из которых конструктор «Срезы» читает. Сам импорт отчётом не является.

## 8. Объём

`GetData` перед выборкой вызывает `GC.Collect()` и `GC.WaitForPendingFinalizers()`. Через 60 секунд таймер отменяет команду, закрывает соединение сессии и делает `Thread.Abort`. Сообщение пользователю: «Время выполнения запроса превысило допустимый предел.» `CommandTimeout` на команде не задан. `ExecuteScalar` и `ExecuteQuery` этого таймера не имеют.

Лимита строк нет: адаптер заполняет `DataTable` целиком, затем сводная и график работают по этой таблице. Обязательного фильтра по дате конструктор не ставит.

Корни, которые уже оценены по словарю:

| Корень | Объём из словаря |
| --- | --- |
| `STATEREPORTRECORDS` | больше 1 млрд строк, без PK и без партиций |
| `WAGONDOWNTIME` через `WAGONDOWNTIMEVIEW` | около 184 млн |
| `STATEREPORTSWAGON` | около 8,2 млн, в key-set индексов не было |

«Анализ» после `ReportsPkg.GetLastRepairs` для каждой строки курсора вызывает `ReportsPkg.GetLastTORs`.

Журнал службы пишет весь текст запроса, имя пользователя, код сессии и число строк (`### GETDATA START ###` / `FINISHED`).

## 9. Уязвимости, которые видны в коде

Текст ниже описывает найденные места. Готовых запросов для проверки нет, и их не нужно собирать вручную на этой базе.

**Подстановка в SQL.** Условия, `IN`-списки, операнд арифметики и `JoinString` / имя поля из метаданных склеиваются в `CommandText`. Кавычки в строковом условии не удваиваются. Числовой массив не проверяется как число. Служба выполняет получившийся текст от имени соединения сессии, то есть учётной записи службы, а не отдельной роли «только отчёт».

**Обход пункта меню.** Флаги `CreateDynamicReports`, `PlannerReportConstructor`, `WarehouseReportConstructor` и `ViewDynamicReports` закрывают кнопки. `GetData`, `ExecuteScalar` и `ExecuteQuery` флаг не проверяют: им достаточно живой сессии. Любой уже вошедший клиент пользуется тем же методом, что и конструктор.

**Утечка в журнал.** В журнал попадает полный SQL вместе со значениями фильтров и код сессии. Туда же пишется ошибка со стеком.

**Тяжёлый запрос.** Нет ограничения строк и нет обязательного периода. Корни — таблицы срезов и простоев. Таймаут 60 с закрывает соединение сессии. Параллельный импорт срезов пишет ту же `STATEREPORTRECORDS`.

**Файл отчёта.** `.brp` читается `BinaryFormatter`, `.rep` — `SoapFormatter`, без белого списка типов. Раскладка сводной восстанавливается из тех же байтов. Файл открывает тот, у кого есть конструктор.

**Дата справки инвентаря.** `ReportDate` попадает только в заголовок Excel. `RepairReportsPkg.FillStateInventory` и соседние процедуры вызываются без параметров. Какой день считает пакет, из spec не видно.

## 10. Что можно взять заново и что надо переписать

Пригодно как устройство, код переносить целиком нельзя:

- Дерево полей по номеру приложения и отдельный экземпляр отчёта (поля, условия, раскладка сводной).
- Набор типов поля и операторов сравнения.
- Готовый отчёт как форма параметров плюс вызов процедуры с привязанными параметрами (`StaticalReport`, `PropertyAttribute`, `ExecuteNonQueryCursor`).
- Выгрузка уже полученной сетки отдельным шагом после выборки.

Нужно переписать:

- Сборку SQL конкатенацией и исполнение произвольного текста в `GetData` / `ExecuteScalar` / `ExecuteQuery`.
- Проверку права только на кнопке. Право должно стоять на выполнении отчёта.
- Хранение отчёта через `BinaryFormatter` и `SoapFormatter`.
- Загрузку всего курсора в `DataTable` без предела строк и без обязательного периода на больших корнях.
- Таймаут через `Thread.Abort` и закрытие соединения сессии, а также `GC.Collect` на каждый запрос.
- Запись полного текста запроса в журнал.
- `CheckReportFields`: обход дерева обрывается на первой вложенной группе.
- Справку инвентаря: дата не передаётся в процедуры; в пакете есть `FillRepairPlantsZiksto`, `FillRepairPlantsBogatyrTrans` и `FillTransitionDates`, клиент их не вызывает.
- Движение вагонов: код ищет `.xlt`, в каталоге шаблон `.xsl`.
- Excel через COM и пункты, которые просто открывают `.xlt`.
- Пустые `ExecuteReportData` и `PlatformStateReportsJob`.
- «Анализ»: отдельный вызов `GetLastTORs` на каждую строку.

## 11. Чего в поставке нет

- Тел `ReportingPackage`, `ReportsPkg`, `RepairReportsPkg`, `ReportExecution`, `ReportRoutes`, `RequestPackage`.
- Строк каталога полей (курсоры `GetFields` / `GetTables` / `GetGroups` не читались).
- Сохранённых пользователями `.rep` / `.brp` и содержимого реестра информационной панели.
- Запросов внутри книг `Availability.xlt`, `AvailabilityMoths.xlt`, `CargoWork.xlt`, `LoadingFact.xlt`, `LoadingPlanFact.xlt`.
