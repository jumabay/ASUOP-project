# НУД: модель детали, склада и документа

Источник — копии `WarehouseApp` 1.2.0.29, `WarehouseLib`, `WagonLib` и spec `WarehousePkg` / `PartsPackage`. Тела пакетов не читались. Объёмы таблиц ниже не пересчитывались: где число уже было в снимке этапа 2, оно помечено как снимок.

## 1. Цепочка, которая подтверждена

```
тип детали (PARTTYPES, модель 0…3)
    → экземпляр (WAGONPARTS: номер, клеймо, год) или металл (METAL, без номера)
        → остаток (WAREHOUSEDETAILS на WAREHOUSES)
            → строка документа (*DETAILS)
                → шапка документа (покупка / приход / перемещение / списание / ремонт КП / ведомость / ремонт склада)
                    → вагон и ремонт вагона только если строка списания или строка ведомости несёт repair_id
```

Складской «документ ремонта» и строка `REPAIRS` УВП — разные объекты. Общий ключ между ними на экране НУД — `detail_id` и, для списания и ведомости, `repair_id`.

## 2. Деталь и номер

`DetailType` («Типы деталей»): вес, марка металла (`STEELDEGREE`), модель, нормативное количество, горячая клавиша, срок службы. Запись — `PartsPackage.SaveDetailType`.

Модели совпадают у клиента и у пакета:

| Код | Клиент | Учёт |
| --- | --- | --- |
| 0 | `Detail` | количество, без номера. `SaveDetail(id, detailtype_id)` |
| 1 | `WheelPair` | номер, клеймо, год. `SaveWheelPair` |
| 2 | `ManufactoringDetail` | номер, клеймо, год. Срок службы на карточке только читается. `SaveManufactoringDetail` |
| 3 | `HatchCover` | номер чертежа, не заводской номер. `SaveHatchCover` |

Типы детали в пакете (это не модель): 0 колёсная пара, 1 автосцепка, 2 надрессорная балка, 3 боковая рама. На форме типа детали код задаётся полями справочника, клиент эти четыре подписи сам не рисует.

Номер живёт в `WAGONPARTS`. Триггер `TR_WAGONPART_ID` выдаёт id. Карточка колёсной пары ограничивает номер 15 символами, клеймо — 5. Повтор номера клиент не проверяет. `PartsPackage.GetDetailId(id, partnumber, detailtype_id)` в сборках НУД не вызывается.

Отдельные процедуры загрузки, которые НУД не вызывает, ищут существующую строку так: `partnumber` + `type`, `rownum = 1`, иначе `INSERT` в `WAGONPARTS`. Клеймо в этот поиск не входит. Это правило загрузчика, не правило экрана. Уникального ограничения по номеру словарь этого прохода не показывает.

Второй вид запаса — металл (`ObjectType = 1`, справочник `METAL`). У него нет номера. На остатке и в строках прихода, перемещения, списания и ремонта склада тип объекта различает деталь и металл.

## 3. Склад

`Warehouse`: имя, ремонтное предприятие, тип склада. Запись `WarehousePkg.SaveWarehouse`, список `WAREHOUSESVIEW`, удаление `DeleteWarehouse`.

Константы пакета: тип 0 основной, тип 1 склад ответственного хранения. Экран показывает имя из `WAREHOUSETYPES` и не подписывает эти коды. `SP_TRANSFERWAGONPART` (не кнопка НУД) ищет склад предприятия `repairplant_id = 9934` с типом 0 и склад получателя с типом 1.

`WAREHOUSEDETAILS` — остаток. Чтение `LoadWarehouseDetails(warehouse, detailtype)`. В снимке этапа 2 у `WAREHOUSES` 41 строка. Мест внутри склада нет.

Виртуальный запас — `VIRTUALWAREHOUSEDETAILS` (снимок этапа 2, около 659 тыс. строк). Оборотная ведомость его читает. Процедура, которая кладёт туда детали «до ремонта» (`AddBeforeToVirtualWarehouse(repair_id)`), из НУД не вызывается.

## 4. Документ и операция

Операция учёта — документ одного из семи видов. Черновик и проведённый экземпляр различаются `Register_Type`: 0 и 1. Проводка меняет остатки внутри тела `Register*`; текст тела закрыт, поэтому состав обновления `WAREHOUSEDETAILS` здесь не утверждается.

| Вид | Код | Шапка | Строка | Что отличает операцию на экране |
| --- | --- | --- | --- | --- |
| Покупка | 0 | склад, дата, контрагент | деталь, состояние покупки, количество, клеймо, дата, толщины | приход от поставщика, новые номера создаются карточкой детали |
| Приход | 1 | склад, дата | тип объекта, состояние, причина несоответствия, количество, деталь, клеймо, дата, толщины | оприходование уже известной или новой детали и металла |
| Перемещение | 2 | склад-получатель, дата, склад-отправитель | тип объекта, количество, деталь, состояние покупки | строки только из остатка отправителя |
| Списание | 3 | склад, дата, тип списания, причина, связанный id | то же плюс `repairid` и причина строки | продажа пишет в связанный id контрагента; ремонт вагона пишется в строку |
| Ремонт колёсной пары | 4 | тип ремонта, пара, новые номер и клеймо, дата, толщины, склад пары | деталь, количество, склад, тип объекта | смена оси или колеса — константы 1 и 2, подпись берётся из справочника |
| Оборотная ведомость | 5 | склад, период | деталь, тип прихода, ремонт, дата операции | строки из виртуального запаса |
| Ремонт склада | 6 | склад, дата, склад-отправитель | как приход | складской документ, без id ремонта вагона |

Удаление документа на клиенте не смотрит на проводку. Запрет проведённого удаления может быть только в теле `Delete*`.

Отдельной операции «возврат» и отдельной операции «сменить статус» нет. Статус документа — проводка. Статус детали на строке — `DETAILSTATES` или `BUYINGSTATES`. Значок истории — результат `GetHistoryState`, пользователь его не редактирует.

## 5. История

`LoadPartHistory(id)` возвращает набор с полями `history_date` и `history_text`. Форма показывает их как «Дата» и «История». Входит ли в текст строка ремонта вагона, строка склада или обе, по spec не видно: тип возврата `partspackage$history_set` объявлен, состав колонок конвейера в spec не расписан.

Щелчок по значку заново читает этот курсор. Пустой результат клиент считает «новой» деталью, непустой — «бывшей в употреблении».

## 6. Связь с вагоном, ремонтом и УВП

Подтверждённые стыки:

| Откуда в НУД | Куда | Ключ |
| --- | --- | --- |
| строка списания `repairid` | `IWagonCall.LoadRepair`, затем вагон по `OwnerId` | id ремонта УВП. Код вагона на строке только для показа |
| строка ведомости `repair_id` | колонка сетки, в `SaveDetailsWorkingSheetPart` | id ремонта, если его вернул `LoadVirtualDetails` |
| шапка списания при типе «продажа» | `Partner` | `AssociatedObject_Id` |
| любая номерная строка | `WAGONPARTS` | `detail_id` |
| остаток и карточка детали УВП | тот же `GetHistoryState` / `LoadPartHistory` | id детали |
| документ ремонта склада | `REPAIRDOCUMENTS` | свой id. Это не `REPAIRS.id` |

УВП при сохранении ремонта пишет `PartsPackage.SaveDetailsAfter` / `SaveDetailsRemoved` с тем же `detail_id`, клеймом и толщиной. Проводку склада из карточки вагона УВП не вызывает. НУД строку `REPAIRS` не создаёт.

Загрузчики `SP_ARRIVALWAGONPARTS`, `SP_ARRIVEWHEELPAIR`, `SP_TRANSFERWAGONPART` пишут те же шапки и `WAGONPARTS` напрямую и из клиента не вызываются. Пока нет вызова из приложения, это не операция пользователя.

## 7. Ограничения, которые видны без тела пакета

- Проведённый документ с формы не редактируется.
- Перемещение и списание требуют склад, с которого берутся строки.
- В ремонт колёсной пары форма просит номерную деталь: металл и количественная модель отсекаются сообщением.
- Номер колёсной пары — до 15 символов, клеймо — до 5.
- Копирование из реестра не сбрасывает признак проводки. Если исходный документ проведён, копия открывается без права сохранить.
- Повтор номера одной и той же детали клиент не ловит.
- `SaveDetailsWorkingSheetPart` вызывается по строкам без предварительного удаления старых строк ведомости.

Что может запрещать сервер (двойной остаток, чужой склад, повторная проводка, уникальность номера), из клиента и spec не следует. Это остаётся в теле `Register*` и `Save*`.

## 8. Требования к связи склада и ремонтов в новой системе

Ниже — требования к единой системе. Это не описание текущего НУД. Пункты опираются на разрыв, который уже виден между двумя клиентами.

1. Одна карточка экземпляра. Номерная деталь (модель 1 и 2) имеет один id на склад и на вагон. Ключ поиска, который уже используют загрузчики: номер + тип детали. Клеймо и год — атрибуты карточки, не второй ключ. Количественная деталь, крышка люка и металл остаются другими видами запаса и в этот ключ не смешиваются.

2. Уникальность номера фиксируется явно. Сейчас её нет ни на форме, ни в видимом ограничении словаря. Новая система должна запретить вторую активную карточку с тем же номером и типом и показать существующий id. Правило загрузчика «взять первую строку» переносить нельзя.

3. Складской документ и ремонт вагона — разные документы. У ремонта склада остаются склад, дата и склад-отправитель. У ремонта вагона остаётся строка `REPAIRS`. Связь допускается только ссылкой: строка складского документа хранит id ремонта вагона и id детали. Сведение двух проводок в одну процедуру размажет остаток и карточку вагона.

4. Проводки независимы и идемпотентны. Провести ремонт вагона и провести складской документ можно только отдельными командами. Повтор каждой команды не удваивает остаток. Снятие проводки возвращает остаток и не удаляет историю. Отдельный документ «возврат» заводить только как новую функцию: в НУД его нет, там есть снятие проводки.

5. Списание на вагон обязательно ссылается на ремонт. В текущем клиенте ссылка необязательна и лежит на строке, а шапка для типа «на вагон» пустая. В новой системе тип «на вагон» требует вагон, ремонт этого вагона и деталь из остатка. Код вагона показывается из ремонта, а не вводится вручную. Продажа по-прежнему ссылается на контрагента. Типы «списание», «на колёсную пару» и «на металлолом» не требуют ремонта вагона; металлолом нужно завести явным типом, а не «пустой панелью» для неизвестного id.

6. История детали одна. Лента по id детали содержит складские документы и установку или снятие на ремонте вагона: дата, вид операции, документ, склад либо вагон и ремонт. Значок «новая / уже была» считается по этой ленте, а не двумя разными правилами формы и функции.

7. Виртуальный запас ремонта виден как очередь, а не как скрытая таблица. Детали «до ремонта», которые сегодня попадают в `VIRTUALWAREHOUSEDETAILS`, в новой системе должны открываться ведомостью с id ремонта-источника. Повторное сохранение ведомости заменяет её строки, а не дописывает копии.

8. Остаток хранится на складе ремонтного предприятия и типе склада. Ячеек в старой системе нет, и переносить их неоткуда. Одна и та же номерная деталь не числится положительным остатком на двух складах после проведённого перемещения.

9. Ремонт колёсной пары меняет карточку пары (номер, клеймо, толщины) и списывает израсходованные детали отдельными строками. Он не создаёт ремонт вагона. Если пара после этого ставится на вагон, это уже строка ремонта УВП со ссылкой на тот же id пары.
