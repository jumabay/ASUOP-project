# 06. Стратегия хранения

> **Target store superseded by [ADR-0009](decisions/ADR-0009-raildb-primary-store.md) (Accepted direction, 2026-11-20):** целевой store — `RAILDB` / `RAIL_APP`; окно миграции 12м + FULL/OPEN/REF — [25](25_DBTC_TO_RAILDB_MIGRATION_MATRIX.md). Ниже — **физика и правила legacy `DBTC`**, нужные для миграции и parity. Этот документ не содержит DDL и не разрешает Create/Flyway.

Хранилище **legacy** — схема `DBTC` Oracle 12.2.0.1.0. Объёмы ниже — `NUM_ROWS` / `BLOCKS` из статистики, не `COUNT(*)`. Источник: [02_ORACLE_PERFORMANCE.md](../analysis/02_ORACLE_PERFORMANCE.md).

## Три слоя

| Слой | Объекты | Как живут | Кто пишет сейчас |
| --- | --- | --- | --- |
| Текущее | `WAGON` (~50 тыс.), `GIVING` (~9 тыс.), `WAGONAPPROACH` (~27 тыс.), `CURRENTPARTS` (~168 тыс.) | одна живая строка на объект | старые клиенты, jobs, невидимый `WAGONUPDATEDISL` |
| Час | `IMPORTFILES` → `STATEREPORTS` → `STATEREPORTRECORDS` | заголовок файла и строка на вагон файла | `ImportPkg` «Сервис приложение» |
| Архив и витрины | `WAGONAPPROACHARCHIVE`, `WAGONDOWNTIME`, `GIVINGARCHIVE`, `WAGONMILEAGE`, `STATEREPORTSWAGON`, `WAGONSTATEREPORTS*` | отдельные таблицы, не лента среза | jobs и пакеты, тела не прочитаны |

Быстрый просмотр вагона читает паспорт `WAGON`. История часа читает `STATEREPORTRECORDS` через `StateReportPackage.GetWagonStateReports` и индекс `IDX_REC_WAGON_ID (WAGON_ID, GETTING_DATE)`. Эти два чтения не объявляются равными: запись `WAGON.LOCATION*` из строки среза не доказана, триггера на `STATEREPORTRECORDS` нет (G3, M22).

`STATEREPORTS.LAST` помечает последний срез. Что член `UpdateLastReport` пишет эту колонку, телом не подтверждено. `STATEREPORTSWAGON` (~8,2 млн, индексов в выборке нет) наполняется jobs. Job `FILLSTATEREPROTSWAGONSTATIONS` в состоянии FAILED и выключен. Документный контур `WAGONSTATEREPORTS` / `WAGONSTATEREPORTSRECORDS` (~2,3 тыс. / ~37,7 млн) идёт через `SYS_DOCUMENTS`. Это не FTP-час.

## Объём часа

Ориентир задания: 18 000 вагонов × 24 часа × 365 дней = 157 680 000 полных строк в год, без файла изменений.

Уже лежащая лента сходится с этим порядком:

| | Значение |
| --- | --- |
| Таблица | `STATEREPORTRECORDS` |
| `NUM_ROWS` | 1 215 316 604 |
| `BLOCKS` | 23 386 502 |
| `AVG_ROW_LEN` | 140 |
| Оценка данных | порядка 180 ГиБ и больше (23,4 млн блоков × 8 КиБ, без сжатия и pctfree) |
| `LAST_ANALYZED` | 2026-10-18 |
| Первичный ключ | нет |
| Секции | нет |
| Индексы | 11 и больше |

1,215 млрд / 157,7 млн ≈ 7,7 года полных срезов при 18 000 вагонах. Это проверка порядка, не точный возраст данных: статистика приблизительная, часть строк может быть другими каналами.

`wagons.txt` на 18 334 строки — список публикации слежения, не строки `STATEREPORTRECORDS`. Связь файла с таблицей слежения не доказана.

Рост парка линейный по полному файлу. 30 000 вагонов дают около 262,8 млн полных строк в год. Файл изменений, если он появится как подтверждённая дельта, добавляется сверху и не заменяет полную строку часа.

Рядом, тем же отсутствием секций: `WAGONAPPROACHARCHIVE` ~886 млн, `WAGONDOWNTIME` ~184 млн, `GIVINGARCHIVE` ~44 млн, `WAGONMILEAGE` ~34 млн, `GIVINGLISTCARRIAGES` ~19,7 млн, `DEPARTURELISTCARRIAGES` ~19,8 млн. Эти архивы в оценку 157,7 млн не входят. Их секционирование — отдельное окно DBA после ленты срезов.

## Что не делается с живой лентой

Пока старый импортёр пишет `STATEREPORTRECORDS`:

- вторая копия миллиарда строк не создаётся;
- таблица не секционируется и не перестраивается;
- индексы не удаляются и не добавляются;
- `COUNT(*)` по полной таблице не запускается;
- новый процесс `SaveStateReportLine*` не вызывает;
- отчёт без предиката даты на эту таблицу не исполняется.

Живой просмотр истории идёт по уже существующему индексу `IDX_REC_WAGON_ID` через пакет чтения. Широкие индексы `IDX_STATEREPORTRECORDS_INFO`, `IDX_STATEREPORTRECORDS_LINKS`, `IDX_STATEREPORTRECORDS_DATA` и индексы внешних ключей поддерживаются каждым построчным `SaveStateReportLine*`. Новый писатель этот набор на себя не копирует, пока не снят профиль SQL НУВ.

Заголовок часа уже есть: `IMPORTFILES` (~313 тыс., ключ имени `IDX_IMPORTFILES_FILENAME`) и `STATEREPORTS` (~412 тыс.). Буфер `STATEREPORTRECORDS_TMP` (~492 тыс.) — рабочий объект пакета. Новый код в него не пишет.

## Целевая физическая модель

Включается на копии и только после теста B1 и отдельного окна DBA, до переключения писателя. Документ архитектуры окно не открывает.

Предложение для новой ленты или для перестроенной копии:

- секции по месяцу `GETTING_DATE`;
- уникальность строки часа `(WAGON_ID, GETTING_DATE, канал)` только если эталон B1 не хранит две строки на этот ключ;
- два рабочих индекса: карточка вагона за период `(WAGON_ID, GETTING_DATE)` и доступ от файла `REPORT_ID`;
- загрузка файла массивом параметров, один успешный файл — одна транзакция;
- онлайн-горизонт: 36 месяцев горячих секций, старшие секции сжаты и доступны только для чтения.

Удаление старших секций — отдельное решение. Текущие 1,2 млрд строк уже держат несколько лет, и срок хранения бизнесом не назван. Сжатие и отключение записи в старую секцию не равны удалению. Требование сохранить всю историю выполняется отказом от удаления, пока бизнес не назовёт срок.

Канал в ключе нужен, потому что KZ, TIS RU и третьи стороны зовут одну `SaveStateReportLineKz` с разным типом файла. Тип файла старого контура: 0 KZ, 1 RU, 2 TIS RU, 3 контейнеры, 16 третьи стороны, 23 Excel.

Пока тело `SaveStateReportLineKz` не прочитано, уникальный ключ не объявляется уже существующим правилом пакета. Если эталон хранит две строки на один `(вагон, час, канал)`, уникальный индекс в таком виде не создаётся.

`GETTING_DATE` выбран осью секции, потому что индекс карточки уже начинается с `WAGON_ID, GETTING_DATE`, а заголовок среза хранит `GETTING_DATE`. `LOCATION_DATE` остаётся атрибутом строки. Если образец файла покажет, что час бизнеса живёт только в `LOCATION_DATE`, ось секции пересматривается до DDL.

## Два файла часа

Полный файл KZ — источник полноты часа.

| | Полный KZ | Второй файл |
| --- | --- | --- |
| Маска эталона | `disl_kz*.txt` | `disl_operations*.txt` |
| Тип | 0 | 1 |
| Поля | 20 или 21, табуляция | 11, образец не разбирался |
| Процедура | `SaveStateReportLineKz` | `SaveStateReportLineRu` |
| Роль в новой модели | каждая непустая строка обязана иметь строку часа | отдельный канал, не дельта KZ |

Требование «хранить неизменившийся вагон» выполняется так: если строка есть во входном полном файле, строка часа есть в хранилище. Отбор «вагон не двигался» на стороне нового разборщика не делается. Отсекает ли так старый пакет, покажет сравнение числа строк файла и числа строк `STATEREPORTRECORDS` этого `IMPORTFILES` на копии (G1).

Если позже образец второго файла окажется дельтой KZ, дельта накладывается на уже принятый полный час и не удаляет строки вагонов, которых в дельте нет. Пока образца нет, такое наложение не реализуется.

Пустой файл в `IMPORTFILES` не регистрируется. Это уже поведение C# старого импортёра.

Обрыв посередине TXT у старого сервиса не откатывается. Новый писатель имеет право принять один файл одной транзакцией, если конечный успешный файл совпадает с эталоном по ключам. Судьба флага `IsImportedFile` при обрыве не измерена (G2). Пока G2 открыт, догрузка хвоста тем же именем правилом не является.

## Идемпотентность, пропуск, рост

Ключ файла: `(имя файла, тип среза)`. Повтор ключа не создаёт второй комплект строк.

Календарь ожидаемых часов ведётся по каналу. Полный KZ ожидается каждый час. Отсутствие файла — сигнал в журнале `operations`, не автоматический вызов пакета.

Очередь сообщений для 18 000 строк в час не вводится.

Контроль роста: раз в сутки фиксируются `NUM_ROWS` и `BLOCKS` по статистике крупных таблиц на копии, не `COUNT(*)`. Резервная копия данных — существующий RMAN схемы `DBTC`. Файлы наблюдателя хранятся на диске не меньше 30 суток и в RMAN не подменяют строки среза.

Ремонты `REPAIRS` около 411 тыс. строк — карточки, не почасовой срез. `STATIONS` (~37 тыс., 83 входящих FK) и `CUSTOMERS` (~580, 51 входящий FK) правятся старыми клиентами. Правка станции в новую систему не переносится из-за связности и триггера `TR_STATIONS_CHANGED`.
