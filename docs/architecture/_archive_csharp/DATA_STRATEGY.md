# Стратегия данных

> Superseded by [06_DATA_STORAGE_STRATEGY.md](../06_DATA_STORAGE_STRATEGY.md). Числа и запреты по живой ленте перенесены без изменения смысла.



Хранилище на всём переносе — схема `DBTC` Oracle 12.2.0.1.0. Второй базы нет. Этот документ не содержит DDL и не разрешает его выполнять. Объёмы ниже — `NUM_ROWS` / `BLOCKS` из статистики, не `COUNT(*)`. Источник: [02_ORACLE_PERFORMANCE.md](../../analysis/02_ORACLE_PERFORMANCE.md), [02_ORACLE_TABLES.md](../../analysis/02_ORACLE_TABLES.md).

## 1. Три слоя

| Слой | Объекты | Как живут | Кто пишет сейчас |
| --- | --- | --- | --- |
| Текущее | `WAGON` (~50 тыс.), `GIVING` (~9 тыс.), `WAGONAPPROACH` (~27 тыс.), `CURRENTPARTS` (~168 тыс.) | одна живая строка на объект | старые клиенты, jobs, невидимый `WAGONUPDATEDISL` |
| Час | `IMPORTFILES` → `STATEREPORTS` → `STATEREPORTRECORDS` | заголовок файла и строка на вагон файла | `ImportPkg` «Сервис приложение» |
| Архив и витрины | `WAGONAPPROACHARCHIVE`, `WAGONDOWNTIME`, `GIVINGARCHIVE`, `WAGONMILEAGE`, `STATEREPORTSWAGON`, `WAGONSTATEREPORTS*` | отдельные таблицы, не лента среза | jobs и пакеты, тела не прочитаны |

Быстрый просмотр вагона читает паспорт `WAGON`. История часа читает `STATEREPORTRECORDS` через `StateReportPackage.GetWagonStateReports` и индекс `IDX_REC_WAGON_ID (WAGON_ID, GETTING_DATE)`. Эти два чтения не объявляются равными: запись `WAGON.LOCATION*` из строки среза не доказана, триггера на `STATEREPORTRECORDS` нет (G3, M22).

`STATEREPORTS.LAST` помечает последний срез. Что член `UpdateLastReport` пишет эту колонку, телом не подтверждено. `STATEREPORTSWAGON` (~8,2 млн, индексов в выборке нет) наполняется jobs. Job `FILLSTATEREPROTSWAGONSTATIONS` в состоянии FAILED и выключен. Документный контур `WAGONSTATEREPORTS` / `WAGONSTATEREPORTSRECORDS` (~2,3 тыс. / ~37,7 млн) идёт через `SYS_DOCUMENTS`, это не FTP-час.

## 2. Объём часа

Ориентир ТЗ: 18 000 вагонов × 24 часа × 365 дней = 157 680 000 полных строк в год, без файла изменений.

Уже лежащая лента сходится с этим порядком:

| | Значение |
| --- | --- |
| Таблица | `STATEREPORTRECORDS` |
| `NUM_ROWS` | 1 215 316 604 |
| `BLOCKS` | 23 386 502 |
| `AVG_ROW_LEN` | 140 |
| Оценка данных | порядка 180 ГиБ и больше (23,4 млн блоков × 8 КиБ, без сжатия и pctfree) |
| `LAST_ANALYZED` | 2026-10-18 |
| Первичный ключ | нет |
| Секции | нет |
| Индексы | 11 и больше |

1,215 млрд / 157,7 млн ≈ 7,7 года полных срезов при 18 000 вагонах. Это проверка порядка, не точный возраст данных: статистика приблизительная, часть строк может быть другими каналами (RU, TIS, контейнеры).

`wagons.txt` на 18 334 строки — список публикации слежения, не строки `STATEREPORTRECORDS`. Связь файла с таблицей слежения не доказана.

Рост парка линейный по полному файлу. 30 000 вагонов дают около 262,8 млн полных строк в год. Файл изменений, если он появится как подтверждённая дельта, добавляется сверху и не заменяет полную строку часа.

Рядом, тем же отсутствием секций:

| Таблица | ~NUM_ROWS | Замечание |
| --- | --- | --- |
| `WAGONAPPROACHARCHIVE` | 886 287 013 | архив подхода, статистика 2026-08-26 |
| `WAGONDOWNTIME` | 184 393 064 | простои, путь отчётов |
| `GIVINGARCHIVE` | 43 926 482 | статистика устарела, 2023-07-19 |
| `WAGONMILEAGE` | 33 642 136 | пробег, пишет служба сообщений |
| `GIVINGLISTCARRIAGES` | ~19,7 млн | вагоны списков подачи |
| `DEPARTURELISTCARRIAGES` | ~19,8 млн | вагоны списков уборки |

Эти архивы в оценку 157,7 млн не входят. Их секционирование — отдельное окно DBA после ленты срезов, не часть первой замены импортёра.

## 3. Что не делается с живой лентой

Пока старый импортёр пишет `STATEREPORTRECORDS`:

- вторая копия миллиарда строк не создаётся;
- таблица не секционируется и не перестраивается;
- индексы не удаляются и не добавляются;
- `COUNT(*)` по полной таблице не запускается;
- новый процесс `SaveStateReportLine*` не вызывает;
- отчёт без предиката даты на эту таблицу не исполняется.

Живой просмотр истории идёт по уже существующему индексу `IDX_REC_WAGON_ID` через пакет чтения. Широкие индексы `IDX_STATEREPORTRECORDS_INFO`, `IDX_STATEREPORTRECORDS_LINKS`, `IDX_STATEREPORTRECORDS_DATA` и индексы внешних ключей поддерживаются каждым построчным `SaveStateReportLine*`. Новый писатель этот набор на себя не копирует, пока не снят профиль SQL НУВ.

Заголовок часа уже есть: `IMPORTFILES` (~313 тыс., ключ имени `IDX_IMPORTFILES_FILENAME`) и `STATEREPORTS` (~412 тыс., колонки `GETTING_DATE`, `OPERATING_DATE`, `WAGONCOUNT`, `LAST`, `IMPORTFILES_ID`). Буфер `STATEREPORTRECORDS_TMP` (~492 тыс.) — рабочий объект пакета. Новый код в него не пишет.

## 4. Целевая физическая модель

Включается на копии и только после теста B1 и отдельного окна DBA, до переключения писателя. На промышленной таблице в этот момент по-прежнему работает старый пакет, либо писатель уже заменён на копии и окно согласовано. Документ архитектуры окно не открывает.

Предложение для новой ленты или для перестроенной копии:

- секции по месяцу `GETTING_DATE`;
- уникальность строки часа `(WAGON_ID, GETTING_DATE, канал)`;
- два рабочих индекса: карточка вагона за период `(WAGON_ID, GETTING_DATE)` и доступ от файла `REPORT_ID`;
- загрузка файла массивом параметров, один успешный файл — одна транзакция;
- онлайн-горизонт: 36 месяцев горячих секций, старшие секции сжаты и доступны только для чтения.

Удаление старших секций — отдельное решение. Текущие 1,2 млрд строк уже держат несколько лет, и срок хранения бизнесом не назван. Сжатие и отключение записи в старую секцию не равны удалению.

Канал в ключе нужен потому, что KZ, TIS RU и третьи стороны зовут одну `SaveStateReportLineKz` с разным типом файла. Одна пара `(вагон, час)` без канала смешает эти срезы. Тип файла старого контура: 0 KZ, 1 RU, 2 TIS RU, 3 контейнеры, 16 третьи стороны, 23 Excel.

Пока тело `SaveStateReportLineKz` не прочитано, уникальный ключ не объявляется уже существующим правилом пакета. На живой таблице первичного ключа нет. Ключ — свойство целевой модели после сверки B1, где эталон — фактические строки старого пакета. Если эталон хранит две строки на один `(вагон, час, канал)`, уникальный индекс в таком виде не создаётся: сначала фиксируется расхождение.

`GETTING_DATE` выбран осью секции, потому что индекс карточки уже начинается с `WAGON_ID, GETTING_DATE`, а заголовок среза хранит `GETTING_DATE`. `LOCATION_DATE` остаётся атрибутом строки. Если образец файла покажет, что час бизнеса живёт только в `LOCATION_DATE`, ось секции пересматривается до DDL, не после.

## 5. Два файла часа

Полный файл KZ — источник полноты часа.

| | Полный KZ | Второй файл |
| --- | --- | --- |
| Маска эталона | `disl_kz*.txt` | `disl_operations*.txt` |
| Тип | 0 | 1 |
| Поля | 20 или 21, табуляция | 11, образец не разбирался |
| Процедура | `SaveStateReportLineKz` | `SaveStateReportLineRu` |
| Роль в новой модели | каждая непустая строка обязана иметь строку часа | отдельный канал, не дельта KZ |

Требование «хранить неизменившийся вагон» выполняется так: если строка есть во входном полном файле, строка часа есть в хранилище. Отбор «вагон не двигался» на стороне нового разборщика не делается. Отсекает ли так старый пакет, покажет сравнение числа строк файла и числа строк `STATEREPORTRECORDS` этого `IMPORTFILES` на копии (G1). До этого сравнения новый писатель не включается.

Если позже образец второго файла окажется дельтой KZ, дельта накладывается на уже принятый полный час и не удаляет строки вагонов, которых в дельте нет. Пока образца нет, такое наложение не реализуется.

Пустой файл в `IMPORTFILES` не регистрируется. Это уже поведение C# старого импортёра.

Обрыв посередине TXT у старого сервиса не откатывается: ошибка строки не останавливает цикл, `SaveImportFile` при ошибке возвращает 0 и исключение не бросает, файл уезжает в `processing`. Новый писатель имеет право принять один файл одной транзакцией, если конечный успешный файл совпадает с эталоном по ключам. Судьба флага `IsImportedFile` при обрыве не измерена (G2). Пока G2 открыт, догрузка хвоста тем же именем правилом не является.

Другие каналы того же хоста (TIS, контейнеры, Excel, файлы подачи `SaveGivingReportLine*`) остаются на старом импортёре до отдельного решения. Контейнеры — не срез вагонов.

## 6. Идемпотентность и пропуск

Ключ файла: `(имя файла, тип среза)`, как аргументы `IsImportedFile`. Повтор ключа не создаёт второй комплект строк.

Календарь ожидаемых часов ведётся по каналу. Полный KZ ожидается каждый час. Отсутствие файла — сигнал в журнале Operations, не автоматический вызов пакета. Чинить дыру повторным прогоном того же имени в старый `ImportPkg` нельзя.

Час извлекается из имени и полей файла. Опрос каталога раз в 45 или 60 секунд часом не является.

Очередь сообщений для 18 000 строк в час не вводится: один проход массивом параметров укладывается в час. Очередь рассматривается только если прогон на копии покажет, что приём не успевает за час и при этом блокирует карточку вагона на пуле `Ui`.

## 7. Витрины, которые новый код не пересчитывает

| Job | Расписание | Пакет | Кто читает |
| --- | --- | --- | --- |
| `FILLGIVINGREPORTS` | ежедневно 01:00 | `GivingDepartureReports.FillGivingReports2` | отчёты подачи |
| `UPDATEALLREPAIRDATES` | ежедневно 01:00 | `JobPkg.UpdateAllRepairDates` | даты ремонта в паспорте |
| `FILLKPI` | ежедневно 02:00 | `KpiPkg.FillKpi` | KPI |
| `AVAILABILITY_VIEW_JOB` | ежедневно 12:00 | `ResourcePkg.UpdateAvailabilityView` | наличие |
| `UPDATEWAGONMONTHDISTANCESDAILY` | ежедневно 01:00 | `ResourcePkg.WriteWagonsDistanceDayli` | пробег за месяц |
| `WAGONUPDATE` | каждые 15 минут | `WAGONUPDATEDISL.WAGONUPDATEDISLTIS` | объект не виден |

Отчёт нового хоста читает то, что job уже записал. Сверка отчёта не ставится на время работы `FILLGIVINGREPORTS`. Jobs `ROTATEREPAIRDETAILS`, выключенный `FILLSTATEREPROTSWAGONSTATIONS` и разовые `CreateJob*` / `UPDATEPS_*` для проверки не запускаются.

В каталоге 35 заданий владельца `DBTC`. Многие исторические задания выключены. Новый хост планировщик Oracle не пополняет.

## 8. Соседние объёмы, которые не являются лентой часа

Ремонты `REPAIRS` около 411 тыс. строк — карточки, не почасовой срез. Детали ремонта и складские строки документов (`ARRIVALDETAILS`, `PROCUREMENTDETAILS`, `TRANSFERDETAILS`, `WRITINGOFFDETAILS`, `REPAIRDETAILS`, `WHEELPAIRREPAIR*`) живут в OLTP-таблицах. `WAGONPARTS` — номерной экземпляр. Уникальный индекс номера в снимке не зафиксирован; проектирование ограничения ждёт `ALL_INDEXES` на копии (G15).

`STATIONS` и `CUSTOMERS` — справочники высокой связности. Их объём мал относительно ленты. Правка станции в новую систему не переносится из-за 83 входящих FK и `TR_STATIONS_CHANGED`.

Простой `WAGONDOWNTIME` (~184 млн) и архив подхода (~886 млн) читаются отчётами только с предикатом периода. Полный просмотр этих таблиц из конструктора запрещён тем же правилом, что и для среза.

## 9. Копии и резерв

Промышленная `DBTC` на `tc-asuvp-03` остаётся источником правды для старых EXE. Новые таблицы и секции сначала появляются на копии, отдельным разрешением DBA.

Резервная копия данных — существующий RMAN. Файлы наблюдателя хранятся на диске не меньше 30 суток и в RMAN не подменяют строки среза: это источник повтора разбора, не вторая база.

Учётка нового приложения на чтении не совпадает с `asuvp_thread_*`. У неё нет права `INSERT` в `STATEREPORTRECORDS`, пока не открыта волна записи.
