# Модули платформы

> Superseded by [03_MODULAR_ARCHITECTURE.md](../03_MODULAR_ARCHITECTURE.md) and [04_MODULE_DEPENDENCIES.md](../04_MODULE_DEPENDENCIES.md). Стек C# / Blazor не выбран. Границы модулей и флаги записи перенесены в Java-набор.



Граница модуля — агрегаты, которые нельзя писать с двух сторон, и пакет Oracle, который модуль имеет право вызывать. Все модули живут в одном хосте. См. [SYSTEM_ARCHITECTURE.md](SYSTEM_ARCHITECTURE.md).

Флаг записи по умолчанию выключен. Класс записи не регистрируется в DI, пока флаг модуля и разрешение на DML в копии не открыты вместе. На старте владелец записи — старый контур.

Коды прав — сквозной enum `DirectoriesLib.Items.Users.Operations`. Нумерация начинается с `WriteWagon = 1`. Ниже перечислены коды, которые уже привязаны к экранам. Полный список членов enum в одной декомпиляции не снимался; неизвестный код в новый каталог не добавляется по догадке.

Новый UI проверяет право на сервере до вызова пакета. Старый `RemoteLib.DbManagerCall.GetData` флаг операции не читает: ему достаточно живой сессии. Этот обход не повторяется.

## Reference

Справочники, на которые опираются почти все документы: `STATIONS` (~37 тыс., 83 входящих FK), `CUSTOMERS` (~580, 51 входящий FK), `WAGONTYPES`, `REPAIRPLANTS`, `PARTTYPES`, `CARGOTYPES` / `CARGOKTZ`, `OPERATIONS`, склады `WAREHOUSES` (41 строка).

Чтение разрешено с первой волны справочников. Правка `STATIONS` не переносится: триггер `TR_STATIONS_CHANGED` штампует `LASTCHANGETIMES` для `STATIONSVIEW` и затрагивает всю связность. Справочники предприятий ремонта читаются вместе с карточкой ремонта. Меню НУД, которое их правит, остаётся у `WarehouseApp`.

## Fleet

Паспорт вагона. Таблица `WAGON` около 50 тыс. строк, первичный ключ `ID`, около 19 индексов. Быстрый просмотр актуального состояния — этот модуль: одна строка паспорта, не лента срезов.

Чтение: `WagonPackage.GetWagonByCode`, `GetWagonList`, `GetActiveWagonList`. Поля сверки A2: номер, модель, род, собственник, станция приписки, признак инвентаря.

Поля `LOCATION*`, `CURRENTSTATE_ID` и дата дислокации показываются как «карточка Oracle» и в критерий совпадения со срезом не входят. Их писатель не доказан: рядом с `ImportPkg.UpdateStateReport` работает job `WAGONUPDATE` → `WAGONUPDATEDISL.WAGONUPDATEDISLTIS` каждые 15 минут, объект вызывающему пользователю не виден (G3, G4).

`SaveWagon` и прямое обновление локации в первой волне чтения отсутствуют. Пробег за месяц читается через `GetMonthDistances`. Считает его job `UPDATEWAGONMONTHDISTANCESDAILY` → `ResourcePkg.WriteWagonsDistanceDayli`. Новый код job не вызывает.

Общий центр FK — `WAGON` (27 входящих). НУВ и УВП — один `WagonApp` двух сборок с общим `WagonLib`. Отдельного ремонтного продукта по имени папки нет.

## Dislocation

Единственный модуль, которому позже можно разрешить заменить `ImportPkg`. До теста B1 модуль файл читает и считает, в базу не пишет.

Источник старой логики: `RemoteLib.GivingDepartures.ImportStateReportsFtp` и наследники в «Сервис приложение».

| Канал | Маска эталона | Тип | Процедура строки |
| --- | --- | --- | --- |
| KZ, полный срез | `disl_kz*.txt` | 0 | `SaveStateReportLineKz` |
| RU | `disl_operations*.txt` | 1 | `SaveStateReportLineRu` |
| TIS RU | `disl_vagons_cis*.txt` | 2 | та же `SaveStateReportLineKz` |
| Третьи стороны | `disl_vagons_all_*.txt` | 16 | та же `SaveStateReportLineKz` |
| Контейнеры | `disl_containers_*.txt` | 3 | `SaveStateReportLineContainer`, первая строка пропускается |
| Excel KZ | `*_disl_kz.xls` | 23 | `UpdateStateReportXml` |

Порядок старого приёма: `IsImportedFile` → `SaveImportFile` → `SaveStateReport` → каждая непустая строка → `UpdateStateReport`. Пустой файл удаляется и в Oracle не пишется. Ошибка строки логируется, цикл идёт дальше. Транзакции на весь TXT нет.

Строка KZ — табуляция, 20 или 21 поле: номер вагона, станция дислокации, индекс поезда, дата дислокации, код операции, станция назначения, станция отправления, получатель, отправитель, тип, собственник, НОД, гружёность, рабочее состояние, номер документа, код груза, вес груза, грузоподъёмность, код сообщения, дата операции, контейнеры при 21 поле.

Файл `disl_operations*.txt` — канал RU, 11 полей. Отдельной дельтой KZ он не считается, пока нет образца. В журнале модуля это второй канал, без слияния с типом 0.

`wagons.txt` (18 334 строки у пользовательской копии) — публикация `GivingDeparture.PublishRegistryStateReports`, не строки среза. Модуль дислокации его не подменяет.

Час задаёт файл. Наблюдатель ведёт локальный календарь ожидаемых часов и поднимает сигнал пропуска. Повтор берётся из карантина и только если ключ `(имя, тип)` ещё не зафиксирован. Повтор того же имени в старый `ImportPkg` для «починки» дыры запрещён: флаг мог встать раньше конца файла, а сам файл уже лежит в `processing` (G2).

Каналы TIS, контейнеров и Excel на первой замене писателя не переключаются: у них тот же пакет, но другие маски. Их оставляет старый импортёр, пока KZ-канал не пройдёт B1.

Чтение истории для экрана: `StateReportPackage.GetWagonStateReports`, интервал суток 00:00:00–23:59:59. Пакет зависит от `STATEREPORTRECORDS`. Что вернёт курсор на неполном часе, телом не подтверждено.

## Movement

Подача, уборка, подход, наряды, маршруты, заявки, планы объёмов. Источник — `WagonPlanner` 1.2.2.85 (только папка НУВ) и пакеты `GivingPkg`, `GivingDeparturePackage`, `RemoteGivingDeparturePackage`, `ApproachPkg`, `WorkListsPkg`.

Кнопки форм по цепочке «кнопка → метод → процедура» не разобраны (G10). В проектирование записи модуль не берётся. Чтение списков допускается после того, как в spec отделены `Get*` от `Save*` и `UpdateStateReport`.

`GivingDeparturePackage` словарём зависит от `STATEREPORTRECORDS`. Файлы подачи пишет ещё и импортёр (`SaveGivingReportLine*`). Эти вызовы остаются у «Сервис приложение». `WorkListsPkg.UpdateStateReport` остаётся у старого наряда.

Планировщик строку `REPAIRS` с формы наряда не редактирует. Стык `RepairsPkg.UpdateGivingDepartureRepair` есть в spec; кто вызывает его из живого контура, не подтверждено. Новый модуль этот член не вызывает.

## Repairs

Ремонтный модуль. Отдельного EXE нет: `RepairExplorer` есть и в НУВ 2.2.1.25, и в УВП 2.2.1.26. Эталон поведения кнопок снят с УВП. Равенство IL двух сборок не предполагается (G11).

Виды `RepairsPkg`: 0 ДР, 1 КР, 2 КРП, 3 ТОР, 4 исключение, 5 отстой, 6 УТР, 7 ТР1, 8 ТО3. Предприятия — `REPAIRPLANTS`. Таблица `REPAIRS` около 411 тыс. строк. На каждой вставке и правке срабатывает `TR_REPAIRS_TIME` → `TimesPkg.WriteTime`. Смысл `WriteTime` скрыт.

Чтение, которое модуль может вызвать:

| Экран | Процедура |
| --- | --- |
| Список | `GetRepairList(WagonId, RepairType)` |
| Карточка | `LoadRegularRepair`, `LoadExtendedCapitalRepair`, `LoadCurrentRepair`, `LoadTrashRepair`, `LoadExclusionRepair`, `LoadMaintenanceThreeRepair` |
| Детали | `LoadDetailsBefore`, `LoadDetailsAfter`, `LoadDetailsRemoved`, `LoadRotatedDetails` |
| Текущие и начальные детали | `PartsPackage.LoadCurrentWagonDetails`, `LoadInstalledDetails` |
| График | `GetWagonRepairs` |
| Бюджет, чтение | `RepairBudgetView`, `GetRepairBudgetColumns`, `GetRepairBudgetData` |
| Следующие даты и факт пробега | поля паспорта `[LoadOnlyField]` |

Даты следующего ремонта считает job `UPDATEALLREPAIRDATES` в 01:00 → `JobPkg.UpdateAllRepairDates`. Пробег с линии пишет служба сообщений (`ImportMileage`, `ImportMileageWeb`, `ImportMileageWeb2612`), не форма. Новый код эти процедуры не вызывает. Поля пробега показываются как прочитанные.

Запись, которая остаётся у старого клиента до своей волны: `SaveDepotRepair`, `SaveCapitalRepair`, `SaveExtendedCapitalRepair`, `SaveCurrentRepair`, `SaveTrashRepair` и `PostSave*`, `SaveExclusionRepair`, `SavePreparationLoading`, `SaveMaintenanceThreeRepair`, `Register` / `UnRegister`, `DeleteRepair`, `ConvertToRepair`. Пары перевода, которые шлёт клиент: ТОР↔УТР (6↔3), ДР↔КР (0↔1), ТОР↔ТР1 (3↔7), ТОР↔ТО3 (3↔8). Отсекает ли пакет лишнюю пару, не подтверждено (M4).

УТР пунктом «Добавить» не создаётся. Проводка не вызывает `Save`: в процедуру уходит уже записанный id. Проведённая карточка на старой форме только для чтения. Клиент при удалении не смотрит признак проводки; запрет на стороне пакета не доказан (G7).

Одна деталь не может быть одновременно в «после» и в «снятых» — правило клиента. `PartsPackage.RotateRepairDetails` с кнопки не вызывается, job выключен, новый код его не запускает.

Бюджет: Excel с формы `RapairBudgetExplorer` Oracle не меняет. Кто вызывает `RepairBudgetPkg.RepairWagon` и `UpdateBudget`, не найдено (G12). Эти члены не переносятся как кнопки.

Исключение и продажа вагона как данные карточки пишутся с вкладки «Дополнительные данные» через `SaveWagon`, не только через `SaveExclusionRepair`. `SP_WAGONEXCLUDE` клиент не вызывает.

## Warehouse

Номерной складской учёт. Источник — `WarehouseApp` 1.2.0.29, пакет `WarehousePkg`, общие детали — `PartsPackage` и таблица `WAGONPARTS`.

Виды документов: 0 покупка, 1 приход, 2 перемещение, 3 списание, 4 ремонт колёсной пары, 5 оборотная ведомость, 6 документ ремонта склада. Документ вида 6 не является строкой `REPAIRS` и не вызывает `RepairsPkg.Register`.

Модели детали: 0 количество, 1 колёсная пара, 2 изготовленная, 3 крышка люка. Экземпляр лежит в `WAGONPARTS`. Уникальность номера в снимке индексов не зафиксирована (G15). Новый код ограничение не выдумывает.

Чтение: `GetDocumentList` (период по умолчанию 31 день), `LoadWarehouseDetails`, `GetHistoryState`, `LoadPartHistory`. Число `GetHistoryState` сравнивается как число. Значок 0/1/2 и метка пустого курсора `New` расшифровке не подлежат, пока не закрыт G16.

Остатки — `WAREHOUSEDETAILS`. Текущие детали на вагоне (`CURRENTPARTS`, около 168 тыс.) отделены от складского регистра. Виртуальный склад `VIRTUALWAREHOUSEDETAILS` (около 659 тыс.) читается через `LoadVirtualDetails`. Кто пишет `AddBeforeToVirtualWarehouse`, из НУД не вызывается (G13). Ведомость нельзя считать самодостаточной.

Единственная ссылка документа склада на id ремонта — строка списания, если ремонт выбран в диалоге. Для типов списания 2…5 панель связанного объекта на форме пустая (M9). Новый экран пустой id не подменяет.

Автономные `SP_ARRIVALWAGONPARTS`, `SP_ARRIVEWHEELPAIR`, `SP_TRANSFERWAGONPART` пишут те же семейства таблиц и клиентом не вызываются. Рабочим API модуля они не являются.

Проводка склада и проводка ремонта делят деталь и не делят документ. Модуль склада `RepairsPkg.Register` не вызывает.

## Reports

Отдельного хоста отчётов нет и в новой системе он не заводится: отчёты — модуль того же монолита на пуле `Report`.

Два канала старого контура, которые не сливаются:

- конструктор собирает `SELECT` и исполняет его через `GetData` (`CommandType.Text`);
- готовый отчёт вызывает процедуру через `ExecuteNonQueryCursor`.

Новый модуль произвольный текст не исполняет. Конструктор заменяется каталогом полей. Корни старого каталога, которые надо закрыть белым списком: `Wagon` (1), `GIVINGLISTSVIEW` (2), `WAREHOUSESVIEW` (4), `STATEREPORTRECORDS` (5), `WAGONDOWNTIMEVIEW` (6), `GIVING_ROUTE_REPORT_VIEW` (9), `STATEREPORTSWAGON` (11). На корнях 5 и 6 обязателен период. `ORDER BY` у старого запроса данных нет, порядок строк в сверку не входит.

Метаданные колонок читаются, когда будет разрешён вызов `ReportingPackage.GetGroups` / `GetTables` / `GetFields`. Выражения, имя которых начинается с `(`, переносятся как есть (G18). Живых `.rep` / `.brp` в поставке нет (G19). `.brp` и `BinaryFormatter` не принимаются.

Готовые отчёты переносятся по одному, после ночных jobs, сверкой курсора, не оформления книги.

| Отчёт | Процедура | Шаблон | Статус переноса |
| --- | --- | --- | --- |
| План погрузки | `RequestPackage.GetLoadingCalendarReport`, `GetLoadingEvenReport` | клиент считает строку «ИТОГО» | чтение готово как тест A10 |
| Планируемые объёмы | `ReportRoutes.GetReportPlan` | `VolumePlans.xlt` | после тела пакета |
| Выполнение плана | `ReportExecution.GetReportExecution` | `ExecutionVolumePlans.xlt` | отношения клиент не пересчитывает |
| Реализация | имя `ReportsPkg.GetDailyRealizationReport` строкой | `RealizationReport.xlt` | члена в снятом spec нет (G21) |
| Движение | `ReportsPkg.GetMovementWagons` | код ищет `.xlt`, лежит `.xsl` (M15) | курсор можно сверять, книгу нельзя |
| Инвентарный парк | шесть `RepairReportsPkg.Fill*` без параметров | `InventoryStateReport.xltx` | дата только в заголовке Excel (G22) |
| Анализ | `GetLastRepairs`, `GetLastTORs` | сетка | заблокирован расхождением M18 |
| Пять книг меню НУВ | запроса в C# нет | `Availability.xlt`, `AvailabilityMoths.xlt`, `CargoWork.xlt`, `LoadingFact.xlt`, `LoadingPlanFact.xlt` | ждут извлечения SQL (G20) |

`PlatformStateReportsJob` отчёт не формирует. Асинхронный контур `ExecuteReportData` бросает `NotImplementedException`. Оба не переносятся.

Витрины, которые кормят отчёты, пишет Oracle: `FillGivingReports2` 01:00, `KpiPkg.FillKpi` 02:00, `ResourcePkg.UpdateAvailabilityView` 12:00, `JobPkg.UpdateAllRepairDates` 01:00. Модуль эти процедуры не вызывает.

Дефекты старого конструктора в эквивалентность не входят: обход только первой вложенной группы, кавычки строкового условия, числовой массив в `IN`. Новая реализация этот канал не повторяет.

## Operations

Журнал действий, технический лог, мониторинг пропущенных часов, карантин и повтор.

Старый журнал пишет полный SQL со значениями фильтров. Новый журнал пишет: кто, какой экран, какой ключ объекта, успех или код ошибки, имя файла и час. Текст запроса и значения фильтров не пишутся.

Повтор файла: из каталога `quarantine`, если ключ `(имя, тип)` не зафиксирован. Повтор проведённого ремонта, проведённого документа и сообщения 2612 не выполняется, пока идемпотентность не измерена.

Сигнал пропуска часа виден оператору. Автоматическая «починка» прогоном того же имени через старый `ImportPkg` запрещена.

Мониторинг хоста: процесс жив, флаги записи выключены, календарь часов, размер карантина. Метрики не читают промышленную сессию импортёра.

## Карточки переноса

Для каждой функции: источник, требование, реализация, тест, совпадение, условие включения. Группы A и B раскрыты в [TEST_STRATEGY.md](TEST_STRATEGY.md). Оба писателя в одну базу одновременно не пускаются.

### Полный почасовой срез

- Источник: `ImportStateReportsFtp` → `SaveStateReportLineKz`.
- Требование: каждая непустая строка файла, включая вагон без смены станции и операции, если строка в файле есть. Правило «писать ли неподвижный вагон» внутри пакета не прочитано (G1). Эталон — результат старого пакета, не догадка.
- Реализация: наблюдатель считает строки локально. Писатель в `DBTC` появляется после тела пакета, образца файла и теста B1.
- Тест: B1.
- Совпадение: число строк и ключи `IMPORTFILES`, `STATEREPORTS`, `STATEREPORTRECORDS` (имя файла, тип, код вагона, время дислокации, станция, операция). Лишняя строка — провал. Пропуск строки, которую старый пакет сохранил, — провал.
- Включение: B1 на двух копиях, промышленный DML не использовался. До этого писатель — «Сервис приложение».

### Второй файл часа

- Источник: `ImportStateReportsFtpRu`, маска `disl_operations*.txt`, тип 1, `SaveStateReportLineRu`.
- Требование ТЗ «файл изменений каждый час» этим каналом не подтверждено (M2).
- Реализация: отдельная строка календаря каналов, без слияния с KZ.
- Тест: отдельный прогон, когда появится образец.
- Совпадение: ключи своего типа, без удаления строк полного часа KZ.
- Включение: после явного решения, что файл — дельта KZ или отдельный контур RU.

### История вагона за сутки

- Источник: `GivingDeparture.GetWagonStateReports` → `StateReports.LoadWagonStateReports` → `StateReportPackage.GetWagonStateReports`.
- Требование: за сутки видны строки часа, которые старый пакет уже сохранил, в том числе без движения, если они есть в курсоре.
- Реализация: экран читает тот же пакет, пул `Ui`.
- Тест: A1.
- Совпадение: число строк и ключи (вагон, время дислокации, станция, операция, id отчёта). Пустой курсор с обеих сторон — совпадение. Порядок строк не сравнивается.
- Включение: после A1 на копии. Старый НУВ не выключается. Успех A1 не открывает B1.

### Быстрая карточка

- Источник: `WagonPackage.GetWagonByCode` / `GetWagonList`.
- Требование: паспорт открывается без чтения ленты срезов.
- Реализация: модуль Fleet, одна строка `WAGON`.
- Тест: A2.
- Совпадение: номер, модель, род, собственник, станция приписки, признак инвентаря. Текущая станция, `CURRENTSTATE_ID` и дата дислокации в тест не входят.
- Включение: вместе с A1, без `SaveWagon`.

### Подача, уборка, подход, наряды

- Источник: классы `GivingDepartures` в `WagonPlanner`, пакеты `Giving*`, `ApproachPkg`, `WorkListsPkg`.
- Требование: история движений, прибытия, подачи и уборки. Кнопки не разобраны (G10), поэтому требование нельзя закрыть переносом имён.
- Реализация записи отложена. Чтение — после разделения процедур в spec.
- Тест: отдельный, после G10. В группу A до этого не входит.
- Совпадение: задаётся по курсору конкретной `Get*`-процедуры, когда она отделена от `Update*`.
- Включение записи: после G10 и своего теста. `UpdateStateReport` нарядов и `SaveGiving*` импортёра остаются у старого контура.

### Ремонт, предприятия, операции, детали

- Источник: `RepairExplorer`, `RepairsPkg`, `PartsPackage`, `RepairBudgetPkg`.
- Требование: список видов 0…8, карточка, детали до/после/снятые, предприятие, даты. Пробег и следующие даты показываются, не пересчитываются.
- Реализация: чтение списка и карточки. Запись ТОР без проводки — волна B4. Проводка — волна B5 после наблюдения G6.
- Тесты: A3, A4, A5, затем B4, B5.
- Совпадение чтения: id и вид каждой строки, множества id деталей, пересечение «после» и «снятые» пусто с обеих сторон, поля `[LoadOnlyField]` равны считанным.
- Включение чтения: после A3–A5. Включение записи: B4, затем B5. `Register` в тестах чтения не вызывается. Оба `Register*` (ремонт и склад) новым вызовом не дублируются.

### Номерной склад

- Источник: `WarehouseApp`, `WarehousePkg`, `PartsPackage`.
- Требование: реестр документов 0…6, остаток, история номерной детали, ссылка списания на ремонт только если ремонт выбран.
- Реализация: чтение реестра, остатка и истории. Запись прихода — B6. Списание со ссылкой на ремонт — B7.
- Тесты: A6, A7, A8, затем B6, B7.
- Совпадение чтения: id документа и признак проводки, ключ детали и количество, пары `history_date` / `history_text` и число `GetHistoryState`.
- Включение записи: B6, затем B7. Складской `Register*` не вызывает ремонтный `Register`.

### Готовые отчёты

- Источник: шаблоны НУВ и процедуры из таблицы модуля Reports.
- Требование: тот же курсор на тот же день и те же параметры после ночных jobs.
- Реализация: по одному отчёту, пул `Report`, оформление Excel в критерий не входит.
- Тесты: A9, A10. Анализ A11 после закрытия M18.
- Совпадение: число строк курсора и значения колонок, которые старый клиент пишет в лист. Строка «ИТОГО» плана погрузки сравнивается отдельно как сумма клиента.
- Включение: отчёт включается роли после своего теста. Job витрины остаётся единственным пересчётом. Книги `Process.Start` ждут G20.

### Настраиваемые отчёты

- Источник: `ReportConstructorForm`, `QueryBuilder`, корни приложений 1, 2, 4, 5, 6, 9, 11.
- Требование: пользователь собирает отчёт из разрешённых полей. Произвольный SQL запрещён.
- Реализация: каталог полей, обязательный период на срезах и простоях, свой пул.
- Тест: A12 на живом `.rep` пользователя.
- Совпадение: число строк и значения выведенных полей. Порядок не сравнивается. Сводная и график не сравниваются.
- Включение: после G19 и только на копии с узким периодом. На сессию импортёра отчёт не садится.

### Пользователи и роли

- Источник: `DirectoriesLib.Items.Users.Operations`, таблицы `USERS` / `PERMISSIONS`.
- Требование: пункт закрыт тем же кодом права, что и в старом клиенте. Проверка на сервере.
- Реализация: модуль Access, флаг до вызова пакета.
- Тест: роль без права не открывает пункт и не вызывает пакет.
- Совпадение: код права и экран из таблицы Access.
- Включение: с первым читающим экраном.

### Журнал, повтор, восстановление

- Источник: поведение TXT-импорта без транзакции и журнал службы, куда попадал полный SQL.
- Требование: пропущенный час виден, повтор не двоит зафиксированный файл, журнал не содержит запрос.
- Реализация: модуль Operations, локальный календарь и карантин.
- Тест: B2 для пустого файла (наблюдение старого сервиса); повтор имени — часть B1.
- Совпадение: пустой файл не создаёт `IMPORTFILES`. Повтор того же имени не добавляет второй комплект.
- Включение писателя — тем же условием, что B1. Обрыв на середине (B3) остаётся закрытым, пока не закрыт G2. «Догрузить хвост» правилом не объявляется.

Провал теста группы A останавливает соответствующий экран. Провал B1 останавливает замену импортёра. Успех A1 замену импортёра не открывает.
