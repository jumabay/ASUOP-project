# План переноса

> Superseded by [17_MIGRATION_ROADMAP.md](../17_MIGRATION_ROADMAP.md). Порядок волн сохранён. Технология хоста — Java, не Blazor.



Порядок задают писатели и общие ключи. Удобство экрана порядок не меняет. Волны совпадают с шагами [08_CROSS_SYSTEM_MATRIX.md](../../analysis/08_CROSS_SYSTEM_MATRIX.md). Приложение и база этим документом не создаются.

Смежные документы: [SYSTEM_ARCHITECTURE.md](SYSTEM_ARCHITECTURE.md), [MODULES.md](MODULES.md), [DATA_STRATEGY.md](DATA_STRATEGY.md), [TEST_STRATEGY.md](TEST_STRATEGY.md).

## 1. Один писатель

На каждый агрегат один владелец записи. На старте всех волн владелец — старый контур.

| Агрегат | Владелец, пока волна записи не открыта | Чем опасен второй писатель |
| --- | --- | --- |
| Срез `disl_*` | «Сервис приложение», `ImportPkg` | повтор имени пропустит файл или допишет строки; `CreateJob*` плодит задания |
| Карточка `WAGON` | старый `WagonApp`, `SaveWagon`; локацию может писать `WAGONUPDATEDISL` | расхождение станции нельзя отличить от job |
| Проводка ремонта | УВП, `RepairsPkg.Register` | тело не прочитано, идемпотентность не доказана |
| Проводка склада | НУД, `WarehousePkg.Register*` | делит деталь с ремонтом и не делит документ |
| Пробег и детали 2612/2731 | «Сервис пользователя» | повтор сообщения может задвоить строки (G8, не измерен) |
| Витрины | jobs Oracle | новый пересчёт встанет рядом с ночным job |

Новый хост при старте проверяет, что флаги записи выключены. Если в конфигурации указан живой старый импортёр, процесс писателя среза не поднимает. Конфиги «Сервис приложение» и «Сервис пользователя» не копируются друг в друга.

Два писателя в одну базу в тестах группы B не пускаются: эталон на копии-1, новый код на копии-2 с тем же пустым началом, либо последовательные прогоны со сбросом копии.

АСУОП и MSSQL `terminal` в волны не входят. Сообщения 2610/2612/2731 остаются на старой службе, пока не прочитаны `ImportMileage*` и `ImportWagonParts2731` и не измерен G8.

Каналы TIS, контейнеров и Excel остаются на старом импортёре после замены одного KZ. Их переключение — отдельные решения после B1, не часть волны 7.

## 3. Переключение пользователей

Переключение идёт по роли и экрану. База одна. Обратная выгрузка строк не делается.

1. Роль с правом чтения получает экран Blazor рядом со старым EXE. Старый EXE остаётся установленным.
2. Сверка на копии (группа A) проходит до показа экрана этой роли на данных копии. Промышленный показ чтения — только после отдельного разрешения смотреть промышленную схему read-only. До этого разрешения экран на промышленные данные не выводится.
3. Экран записи роли не показывается, пока не пройден тест группы B и нет разрешения на DML в копии. Промышленная запись этим разрешением не открывается.
4. Обратный шаг: роль снова открывает старый EXE. Флаг записи нового модуля выключается. Данные не копируются обратно, потому что писатель не менялся или уже один.
5. Старый EXE выключается для роли только когда эта роль больше не пишет и чтение нового экрана совпало с эталоном. Служба импорта выключается последней, после B1 и окна замены писателя.

Готовые отчёты включаются по одному. Роль может видеть новый «План погрузки» и по-прежнему строить «Движение» в старом клиенте.

ClickOnce старых клиентов при запуске может сходить на сервер обновлений. Демонстрации сверки делаются на копии поставки, которую согласует заказчик. Новый хост ClickOnce не использует.

## 4. Ворота записи

Запись не начинается, пока нет всех пунктов списка:

- тело `ImportPkg`, включая `SaveStateReportLineKz`, `UpdateStateReport`, момент установки `IsImportedFile` (G1–G3, G25);
- объект `WAGONUPDATEDISL` найден под учёткой владельца (G4), либо явно решено, что локация карточки в новый модуль не переносится;
- образец `disl_kz*.txt` и, если он есть у заказчика, образец второго файла часа;
- read-only учётка копии, не промышленная сессия;
- тест B1 на двух копиях для замены импортёра;
- наблюдение G6 для проводки ремонта и склада;
- измерение G8 до любого приёма 2612/2731 новым кодом, и не параллельно со старым приёмником.

Пробелы G10 (кнопки планировщика), G19 (живые `.rep`), G20 (SQL книг `.xlt`), G21 (член реализации), M18 (анализ) закрывают свои экраны и не держат волны 0–3.

## 5. Первый этап разработки R0

После отдельного согласия на код. Приложение-хост, Blazor, FTP и Oracle в R0 не создаются. База не меняется.

Состав: библиотека разбора файла KZ и локальный журнал часа. Проверяемый результат — `dotnet test` на синтетической фикстуре по контракту строки из этапа 1.

Фикстура проверяет:

- строка из 20 полей и строка из 21 поля разбираются;
- пустой файл не создаёт запись журнала;
- две строки с одной станцией и одной операцией обе остаются в часе;
- повтор того же имени и типа не создаёт второй комплект в локальном журнале;
- пропущенный час виден в календаре канала.

Фикстура не объявляется образцом промышленного `disl_kz*.txt`. Тест не доказывает, что старый `ImportPkg` сохраняет неподвижный вагон. Он доказывает, что новый разборщик сам строку не выбрасывает и сам ключ не двоит.

К `ImportPkg` и к промышленному FTP шаг не подключается.

Следующий шаг после R0, отдельным согласием: экран карточки и истории суток. Он начинается только при выданной read-only учётке копии и закрывается тестами A1 и A2. До учётки экран не пишется.

## 6. Что не запускается ради проверки

На любой базе, включая копию, без отдельного разрешения и снятого тела:

- `RotateRepairDetails` и полный проход `REPAIRS`;
- `CreateJobUpdateGivingDeparture`, `CreateJobUpdateRegistryMain` и прочие `CreateJob*`;
- второй импортёр в тот же `ImportPkg`;
- произвольный SQL конструктора без периода;
- автономные `SP_*`;
- выключенный `FILLSTATEREPROTSWAGONSTATIONS`;
- разовые `UPDATEPS_*`.

Ночной job на копии, если он включён, остаётся единственным пересчётом дат и витрин. Новый код на время сверки отчёта его не дублирует.
