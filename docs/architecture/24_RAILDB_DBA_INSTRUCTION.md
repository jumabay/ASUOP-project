# 24. Инструкция DBA: создание самостоятельной БД RAILDB

Статус: **черновик для согласования**. Не выполнять создание `RAILDB`, не менять RAC/`DBTC`, не выдавать промышленные пароли в этот документ.

Связано: [ADR-0009](decisions/ADR-0009-raildb-primary-store.md) (PROPOSED), [25_DBTC_TO_RAILDB_MIGRATION_MATRIX.md](25_DBTC_TO_RAILDB_MIGRATION_MATRIX.md).

## 1. Цель

Подготовить **отдельную** Oracle Database **`RAILDB`** как основное хранилище новой платформы. Рабочая схема приложения: **`RAIL_APP` внутри `RAILDB`**.

| Не является целью | Почему |
| --- | --- |
| Схема `RAIL_APP` в существующей RAC | Это схема, не отдельная БД; квота 5 ГиБ непригодна для ленты |
| Изменение `DBTC` / `RAC.WORLD` | Архив и источник миграции; DDL/DML запрещены проектом |
| Автосоздание агентом разработки | Только DBA по отдельному APPROVALS |

## 2. Хост и совместимость

| Параметр | Значение / действие |
| --- | --- |
| Хост (кандидат) | `TC-ASUVP-03` — **подтвердить** CPU, RAM, диск, IOPS, свободное место |
| Существующая БД | RAC, service `RAC.WORLD` — **не изменять** на этапе разработки |
| Версия | Совместимость с клиентом Java: сейчас платформа на `ojdbc10:19.33.0.0` против 12.2; целевая версия instance `RAILDB` — решение DBA (12.2 сейчас или 19c сразу) |
| Charset | Зафиксировать (`AL32UTF8` предпочтителен для нового; если нужна совместимость с `CL8MSWIN1251` DBTC — явное решение + NLS `orai18n`) |
| Лицензия | Проверить, что дополнительный instance/PDB покрыт лицензией |

## 3. Варианты топологии (выбрать один до создания)

### Вариант A — отдельный instance (рекомендуемый для изоляции)

- `ORACLE_SID` / db name: `RAILDB` (имя согласовать, ≤8 символов для SID если требуется).
- Service name (пример): `RAILDB` или `RAILDB.WORLD`.
- Listener: отдельный или shared; **не** подменять service `RAC.WORLD`.
- JDBC пример (без секретов): `jdbc:oracle:thin:@//tc-asuvp-03:1521/RAILDB.WORLD`.

### Вариант B — CDB / PDB на том же сервере

- CDB существующий или новый (решение DBA).
- PDB name: `RAILDB`.
- Service name = сервис PDB (зафиксировать точное имя из `V$SERVICES` после создания).
- JDBC: `jdbc:oracle:thin:@//tc-asuvp-03:1521/<PDB_SERVICE>`.

### Явно запрещено как «целевой prod»

- Использовать только schema `RAIL_APP` внутри текущей RAC без отдельной БД/`PDB`.
- Писать бизнес-данные новой системы в `DBTC`.

## 4. Оценка объёмов (не квота 5 ГиБ)

Источник порядка величины ленты: [06_DATA_STORAGE_STRATEGY.md](06_DATA_STORAGE_STRATEGY.md).

| Величина | Оценка | Комментарий |
| --- | --- | --- |
| Полных строк среза / год | **157,7 млн** | 18 000 × 24 × 365 |
| `AVG_ROW_LEN` ленты (стат.) | ~140 байт | `STATEREPORTRECORDS` |
| Сырые данные 12 мес. ленты | ~**21–25 ГиБ** | 157,7e6 × 140 ≈ 20,6 ГиБ; плюс pctfree/блок-оверхед → ориентир ~25 ГиБ |
| Сверка с живой лентой | ~180 ГиБ / ~7,7 лет ≈ **~23 ГиБ/год** | порядок совпадает |
| Индексы ленты | **×1,5…3** к данным | на DBTC ≥11 индексов; план **×2** → +~50 ГиБ на 12 мес. |
| Итого лента 12м data+index | **~70–100 ГиБ** | консервативно заложить **100 ГиБ** |
| Заголовки `IMPORTFILES`/`STATEREPORTS` | < 1 ГиБ | |
| `WAGON` (~50k), current, parts, refs | < 5 ГиБ | |
| Ремонты 12м + open, складские доки 12м | **5–20 ГиБ** (UNKNOWN без точных NUM_ROWS среза) | заложить запас |
| Ops: intake, errors, audit, quarantine metadata | < 5 ГиБ | файлы карантина — **отдельный диск ОС**, не tablespace |
| Рост год 2 (ещё 12м полных срезов) | +~70–100 ГиБ | если RAILDB копит историю дальше окна миграции |
| Online redo / FRA на время bulk load | **десятки–сотни ГиБ** пиком | спланировать ARCHIVELOG + FRA |
| RMAN full ≈ datafiles | **≥ 150 ГиБ** на старте; с retention 7–14 дней — кратно | не считать «5 ГиБ» |

### Рекомендуемый минимум ёмкости (для согласования)

| Ресурс | Минимум к обсуждению |
| --- | --- |
| Tablespace данных (год 1 + запас) | **≥ 300 ГиБ** usable (лучше 500 ГиБ с autoextend ceiling) |
| FRA / backup area | **≥ 1× full + archive** на политику retention (ориентир **≥ 500 ГиБ** отдельно) |
| Диск карантина файлов (ОС) | **≥ 100 ГиБ** (полные `disl_*` + API dumps ≥ 30 дней) |
| RAM instance | по нагрузке 20–30 UI + bulk migration; гипотеза старта **16–32 ГиБ** — уточняет DBA |

Квота **5 ГиБ** схемы в RAC **отклоняется** как ориентир.

## 5. Учётные записи (least privilege)

| Учётка | Назначение | Права (целевые) |
| --- | --- | --- |
| `RAIL_APP` | runtime приложения на `RAILDB` | `CREATE SESSION`; DML на свои таблицы; **без** `DBA`, без DDL в prod runtime (DDL — Flyway/DBA) |
| `RAIL_MIGRATE` (имя TBD) | инструмент миграции | SELECT на нужные объекты `DBTC` (или роль read); INSERT/UPDATE на `RAILDB.RAIL_APP` migration tables |
| `RAILWAY_READONLY` | не путать | существовала для smoke к RAC; не owner `RAILDB` |

Пароли — только secret store / env; не в Git.

## 6. Backup / recoverability

- Режим ARCHIVELOG для `RAILDB`.
- RMAN: daily incremental + weekly full (политика заказчика).
- Тест restore на копии **до** cutover.
- Отдельно: бэкап `DBTC` продолжает RMAN владельца RAC (не отменяется этим проектом).

- [ ] План отката cutover прочитан (ADR-0009)

## 8. Что DBA **не** делает по запросу разработки без новой строки журнала

- DDL/DML в `DBTC`
- Перенос service `RAC.WORLD`
- Выдача `DBA` приложению
- Автозапуск Flyway из CI без approve
- Удаление схемы `RAIL_APP` в RAC «заодно»

## 9. После создания (сообщить разработке, без паролей в чат)

1. Точный JDBC URL (host/port/service).
2. Вариант A/B и имена SID/PDB/service.
3. Charset / NLS.
4. Факт создания пустой схемы `RAIL_APP` в `RAILDB`.
5. Подтверждение, что `DBTC` не изменялась.
