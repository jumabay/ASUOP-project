# 11. Экспедирование

В материалах этапов 1–10 самостоятельного модуля экспедирования, тарифов и договоров нет. Кнопки заявок и маршрутов `WagonPlanner` разобраны списком классов, не бизнес-правилами (G10). Этот документ задаёт место модуля. Правила перевозок сюда не дописываются.

## Место в монолите

Модуль `expedition`. Зависимость наружу — публичный интерфейс `fleet` (вагон) и позже публичный интерфейс `finance` (передача начисления). Зависимости внутрь от `dislocation` и `repairs` нет, пока отдельное задание их не назовёт.

Пункт меню в React резервируется и остаётся недоступным. REST-заглушки без полей предметной области не публикуются: пустой API создаёт ложный контракт.

## Что модуль сможет принять, когда появятся требования

Имена ниже — границы ответственности, не модель данных и не статусы.

- Заявка на перевозку.
- Маршрут.
- Клиент. Справочник `CUSTOMERS` уже есть в `DBTC` (~580 строк, 51 входящий FK) и принадлежит модулю `reference`. Новый клиентский реестр рядом с ним не заводится, пока не доказано, что это другой объект.
- Станции отправления и назначения. Справочник `STATIONS` уже есть. Правка станций в новую систему не переносится.
- Контроль исполнения, тариф, статус, документ.
- Связь с вагонным парком через id вагона.
- Передача факта в `finance` событием модуля, не прямой записью в таблицы 1С.

## Чего нет и что не делается

- Нет утверждённого жизненного цикла заявки.
- Нет тарифа и нет образца документа.
- Нет решения, заменяет ли модуль экраны `WagonPlanner` или это новый контур поверх них.
- Запись в `Giving*`, `ApproachPkg`, `WorkListsPkg` из `expedition` запрещена. Эти пакеты остаются у `movement` и старого планировщика.
- Таблицы под экспедирование в `DBTC` этим документом не создаются.

Открытие модуля — отдельное задание после волны чтения вагона. До него код модуля не пишется.
