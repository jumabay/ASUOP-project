# 15. Развёртывание и эксплуатация

Один сервер приложений. Oracle `DBTC` уже стоит отдельно (`tc-asuvp-03` для словаря промышленной схемы). Новый процесс к промышленной схеме не подключается, пока нет отдельного разрешения на чтение. Своей базы у хоста нет. Резервная копия данных на всём переносе — существующий RMAN схемы `DBTC`.

## Стартовая конфигурация

Нагрузка, которую нужно держать: 20–30 одновременных пользователей, карточка одного вагона, список порядка 18 тыс. паспортов, разбор файла около 18 тыс. строк реже одного раза в час. Ленту в 1,2 млрд строк приложение не сканирует.

Число ядер и объём памяти промышленного сервера приложений не измерялись. Стартовая гипотеза до нагрузочного прогона, не норма закупки: 4 vCPU и 16 ГиБ ОЗУ на процесс JVM, Oracle на другой машине, диск журнала и карантина файлов отдельно от каталога публикации. Если прогон на копии не уложится в пороги [16_TESTING_STRATEGY.md](16_TESTING_STRATEGY.md), гипотеза пересматривается явно. Увеличивать число процессов до этого прогона не нужно.

Измерения, без которых гипотеза не становится решением:

- 95-й перцентиль карточки и списка на копии с индексом `IDX_REC_WAGON_ID`;
- время разбора локального файла на 18 тыс. строк KZ;
- отчёт одного закрытого дня на пуле `Report` после ночного job, не во время `FILLGIVINGREPORTS`;
- карточка во время разбора файла: порог карточки не должен сломаться;
- занятие пула `Ui` при 30 параллельных запросах карточки.

Полный проход 1,2 млрд строк и конструктор без периода в испытание не входят.

## Каталог и откат

Один каталог публикации на версию, например `app/releases/1.2.3`. Служба Windows или аналог указывает на текущую версию ссылкой. Откат — переключение ссылки на предыдущий каталог и перезапуск процесса. Миграции Flyway по `DBTC` при этом нет, откатывать схему вагонов не требуется. Если позже появится схема метаданных приложения, откат версии запрещён, пока миграция этой схемы не обратима. Пока схемы метаданных нет, откат приложения безопасен: писатель в Oracle выключен.

Секреты лежат вне каталога публикации. Откат их не затирает и не копирует в Git.

Принятые файлы наблюдателя хранятся на диске не меньше 30 суток.

## Доступность и сбои

Процесс при старте проверяет: флаги записи выключены; если в конфигурации указан живой старый импортёр, писатель среза не поднимается. Падение процесса не оставляет второй записи в `ImportPkg`, потому что этой записи нет.

Исключение запроса попадает в журнал кодом, клиент получает короткую ошибку, соединение пула возвращается. Повторный импорт того же имени не создаёт второй комплект в локальном журнале.

Наблюдаемость без отдельного кластера мониторинга на старте: файл журнала, признак живого процесса, календарь пропущенных часов, размер карантина, длительность вызовов белого списка. Централизованный сбор журналов подключается, когда заказчик назовёт приёмник. До этого агент сбора не ставится.

Фоновые задания: наблюдатель файла и отметка пропущенного часа. Их последний успех виден в журнале `operations`. Молчание дольше двух интервалов файла — сигнал, не автоматический вызов пакета.

## Рост

Второй сервер приложений имеет смысл только для чтения и только после того, как одна JVM не держит порог карточки. Оба экземпляра читают одну Oracle. Писатель среза остаётся в одном экземпляре. Балансировщик и общее хранилище сессий до этого измерения не вводятся: при одном сервере сессия живёт в памяти процесса.

Совместимость версий: клиент React публикуется вместе с сервером из того же релиза. Отдельного контракта «старый UI / новый API» на старте нет. OpenAPI лежит рядом с релизом и сравнивается при сборке.

Обновление Java и Spring — плановыми релизами на копии, затем переключение каталога. Промышленная Oracle этим обновлением не затрагивается. Обновление самой Oracle до 19c — окно DBA, см. [05_ORACLE_INTEGRATION.md](05_ORACLE_INTEGRATION.md).

## Резерв и восстановление

| Объект | Как копируется | Как восстанавливается |
| --- | --- | --- |
| Строки `DBTC` | существующий RMAN | процедура DBA, не скрипт приложения |
| Каталог публикации | копия предыдущего релиза на диске | переключение ссылки |
| Журнал часа и карантин файлов | диск сервера приложений, срок не меньше 30 суток | повтор разбора из карантина, не из промышленного FTP |
| Секреты | хранилище вне Git | не восстанавливаются из репозитория |

Потеря каталога приложения не восстанавливает ленту срезов: лента лежит в Oracle у старого писателя. Потеря файла в карантине не лечится повторным прогоном того же имени через старый `ImportPkg`, пока не закрыт G2.
